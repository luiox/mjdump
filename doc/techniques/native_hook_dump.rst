Native Hook 获取 Class Bytes
============================

native hook 可以在 JVM 的类定义或相关运行时边界观察候选 class bytes。它
属于 VM 实现层技术，不是 JVM 或 JVMTI 规范保证的 classfile 获取方式。

问题
----

需要先区分三种不同目标：

- 类定义调用中传入的字节数组；
- 某个 VM 阶段保存的 classfile 副本；
- 已验证、转换或重定义后的字节表示。

它们可能来自不同阶段，保真度也不同。截获到一个缓冲区不等于获得了可独立
重放的原始 classfile。

观察层级
--------

.. list-table::
   :header-rows: 1

   * - 观察点
     - 通常可得数据
     - 主要限制
   * - Java/JNI 类定义边界
     - 定义请求携带的名称、loader 和候选字节
     - 仅覆盖经过该入口的定义路径
   * - VM 导出入口
     - VM 暴露的类定义或查找调用
     - 导出面和调用约定随 VM/构建变化
   * - VM 内部定义路径
     - 更早或更专用的定义数据
     - 符号、布局和时序均是实现细节
   * - 类缓存或元数据
     - 缓存副本、身份或局部代码
     - 可能缺失属性，且生命周期不稳定

选择观察点前应明确需要的是「定义时输入」还是「运行时仍保留的副本」。

.. _techniques-native-hook-lifecycle:

数据生命周期
------------

hook 回调中的字节指针通常只在原调用期间有效。采集方需要在返回前完成受控
长度复制，并在记录中保留类名、loader 身份、定义时机和来源层级。不能把借用
缓冲区交给异步 writer，也不能假设同名类来自同一个类加载器。

目标发现与兼容性
----------------

类定义入口、模块边界、符号可见性和调用约定属于具体 VM、JDK 构建、操作系统
与 CPU 架构的组合事实。技术页面应只说明验证原则：确认模块身份、入口签名、
地址所属映像和真实定义路径；具体函数名、版本选择和注入方式属于产品设计及
能力说明。

JIT 内联、延迟模块加载、多个 VM 实例和运行时重转换都可能改变观察结果。
发现失败或证据不足时，应回退到 Instrumentation、JVMTI 或明确报告不可观测，
而不是猜测地址继续读取。

回调约束
--------

类定义路径可能持有 VM 锁。回调只应复制数据和投递轻量事件；文件 I/O、堆
分配、符号解析、等待和复杂 JNI 操作应由后续线程完成。队列满时必须有预先
定义的丢弃或停采策略，避免阻塞目标 JVM。

.. _techniques-native-hook-boundary:

边界
----

- 该方法通常只适用于已验证目标 VM 和平台，不具有跨 JVM 可移植性。
- Hidden class、重定义、代理和自定义加载路径可能绕过选定入口。
- 采集结果需要由 classfile 解析或加载验证确定其完整性，不能仅凭字节长度
  声明成功。
- 具体 hook 目标、注入和版本选择见产品设计，而非本技术页。
